# データベース運用におけるサービス停止リスクの整理（要約版）

**日付**: 2026-04-02
**対象**: PostgreSQL 17 / ロジカルレプリケーション環境（サブスクライバ側）
**本編**: [2026-04-02_report_service_level.md](2026-04-02_report_service_level.md)

---

## 1. 概要

Webサービスで利用するデータベース（PostgreSQL）を中心に、**どんな場面でサービスが止まりうるか**を整理した資料。サービスは365日24時間稼働を前提とする。

---

## 2. システム構成

```
利用者 → Webサーバ → アプリ → データベース（自社サーバ）
                                    ↑
                          データ同期（レプリケーション）
                                    │
                              データベース（配信元サーバ）
```

- 自社サーバのデータベースは、配信元サーバからデータ同期（レプリケーション）でデータを受け取っている
- 利用者が操作する画面は自社サーバのデータを参照する

---

## 3. 結論と推奨対応

このシステムで特に注意が必要なのは以下の2点:

1. **DB基盤設定は後から変えるとサービス停止が必要** → 初期設計で余裕を持たせる
2. **配信元サーバの障害やデータ同期エラーではデータが遅れるが、画面操作は止まらない** → データ遅延は許容する設計とする

> ※ 縮退運転: 一部機能を制限しつつも、最低限のサービスは提供し続ける運用方式

### 停止の許容基準

| 事象 | 許容するか |
|------|-----------|
| 画面が応答しない（操作不能） | **しない（最優先で防ぐ）** |
| データが数秒〜数分遅れる | やむを得ず許容する |

---

### 3.1 想定外障害（予告なく発生）

日常の運用中に予告なく発生する可能性がある障害。

| 障害 | 影響 | 復旧 |
|------|------|------|
| Webサーバの異常停止 | 全画面が応答不能 | 数秒で自動再起動 |
| アプリのメモリ不足 | 全画面が応答不能 | 自動再起動（数十秒〜数分） |
| DB接続の枯渇 | 画面がタイムアウト | 接続回復で自動解消 |
| 配信元サーバの障害・ネットワーク断 | データが最新でなくなる（画面操作は正常） | 復旧後に自動再接続・差分適用 |
| データ同期エラー（型不一致等） | データが最新でなくなる（画面操作は正常） | 手動対処が必要な場合あり |

---

### 3.2 計画的なシステム変更作業

システムの改修・保守で計画的に実施する作業。サービス停止が必要なものと不要なものがある。

#### サービス停止が必要

| 作業 | 停止時間 | 備考 |
|------|---------|------|
| DB基盤設定の変更 | 数秒〜十数秒 | 初期設計で余裕を持てば発生頻度を下げられる |
| DBメジャーバージョンアップ | 数分 | 手法により数秒に短縮可能 |
| DBマイナーバージョンアップ | 数秒〜1分 | セキュリティ修正等 |
| テーブルの物理再編成 | データ量に依存 | 通常運用では不要なケースが多い |

#### サービス停止が不要

| 作業 | 備考 |
|------|------|
| テーブルへの列追加・削除 | 一瞬ロックがかかるが実質影響なし |
| 列の型変更 | 受信側→配信側の順で作業すれば停止不要 |
| インデックスの再構築 | 専用の方式を使えば影響なし |
| 通常のデータ整理・統計更新 | 自動で定期実行される。影響なし |

---

## 4. 運用上のポイント

1. **初期設計が重要**: DB基盤設定は後から変更するとサービス停止が必要。最初に余裕を持たせる
2. **列の追加・削除は安全**: 列名で自動対応づけされるため、データ同期のエラーにならない
3. **型変更は要注意**: 受信側→配信側の順で作業する手順が必要
4. **データ遅延は許容する設計**: 配信元の障害やデータ同期の一時停止は画面操作に影響しない
