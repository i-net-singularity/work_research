# PgPlanAnalyzer — PostgreSQL実行計画アナライザ (Excel VBA)

PostgreSQLから実行計画を取得し、Excel上でツリー可視化・ボトルネック解析・改善提案を行うマクロ一式。

## 背景 → 核心 → 結論

- **背景**: EXPLAIN (ANALYZE) の出力は情報量が多く、テキストのままではボトルネックの特定に時間がかかる。
- **核心の問い**: どのノードが時間を食い、なぜその実行計画が選ばれ、何を直せば速くなるのか。
- **結論**: 本ツールはプランツリーを時間ヒートマップ付きで描画し、既知のアンチパターン（見積誤差・ディスクスピル・NestedLoop暴走・インデックス欠如等）を自動検出して重大度付きの改善案を提示する。

## セットアップ手順

### 前提条件

1. **Windows版 Excel**（VBAマクロが動く環境。Mac版は未検証）
2. **psqlODBCドライバ**（DB直結機能を使う場合のみ必要）
   - <https://www.postgresql.org/ftp/odbc/releases/> から取得
   - **Excelと同じbit数**（通常は64bit → `psqlodbc_x64.msi`）をインストール
   - インストール後のドライバ名は「ODBCデータソースアドミニストレーター(64ビット)」の
     [ドライバー]タブで確認（例: `PostgreSQL Unicode(x64)`）
   - ※ 貼り付け解析だけ使うならODBCドライバは不要

### 文字コードについて

`src/` 配下のVBAファイルは **Shift_JIS (CP932)・CRLF改行** で保存してある。
VBAエディタのインポートはANSI(日本語環境ではShift_JIS)前提のため、UTF-8のままだと日本語コメント・文字列が化ける。
テキストエディタで開いて保存し直す場合もShift_JISを維持すること
（README・samples・verifyはUTF-8のままでよい。VBAにインポートするのはsrcだけ）。
また、CP932に存在しない記号(⚠や▶等)はコード内から排除済み。

### インポート手順（推奨: 一括インポート）

VBEの[ファイルのインポート]ダイアログは1ファイルずつしか選べないため、同梱のインストーラで一括投入する。

1. Excelのトラストセンター設定を一時的に変更:
   [ファイル] → [オプション] → [トラストセンター] → [トラストセンターの設定] → [マクロの設定] →
   **「VBA プロジェクト オブジェクト モデルへのアクセスを信頼する」にチェック**
   （インポート完了後はチェックを外してよい）
2. Excelで新規ブックを作成 → `Alt + F11` でVBAエディタを開く
3. `src/modInstaller.bas` だけを [ファイル] → [ファイルのインポート] で取り込む
4. `Alt + F8` → `importAllModules` を実行 → フォルダ選択ダイアログで `src` フォルダを指定
   → 残り8本が一括インポートされ、続けて `setupPlanAnalyzer` の実行確認が出る
5. **[名前を付けて保存] → 「Excelマクロ有効ブック (*.xlsm)」で保存**

補足: 最近のMicrosoft 365版VBEはエクスプローラーからプロジェクトエクスプローラーへの
**複数ファイルのドラッグ&ドロップ**によるインポートに対応している場合がある。
使える環境ならトラスト設定不要でそちらが最速（8ファイル選択して落とすだけ）。

### インポート手順（手動: 1ファイルずつ）

1. Excelで新規ブックを作成
2. `Alt + F11` でVBAエディタを開く
3. メニュー [ファイル] → [ファイルのインポート] で `src/` 配下の8ファイル
   （modInstaller.basを除く）を**すべて**インポート
   （順不同でよいが `clsPlanNode.cls` を忘れるとコンパイルエラーになる）
4. `Alt + F8` → `setupPlanAnalyzer` を実行 → シートとボタンが自動生成される
5. **[名前を付けて保存] → 「Excelマクロ有効ブック (*.xlsm)」で保存**

## 使い方

### 方式A: DB直結（自動取得）

1. 「設定」シートに接続情報を入力
   - パスワード欄を**空にしておくと実行のたびに入力を求める**（シートに平文保存しない運用を推奨）
2. 「SQL入力」シートのA3以降に解析したいSQLを貼り付け
3. 「→ DBから実行計画を取得して解析」ボタンを押す

内部では `EXPLAIN (ANALYZE, BUFFERS)`（テキスト形式）を発行する。
※ FORMAT JSONは巨大な1行テキストで返るため、psqlODBCのLongVarChar取得上限
（MaxLongVarcharSize、既定値数KB）で途中切断される事象を確認済み。
テキスト形式は1ノード=1行の複数行結果で返るため切断の影響を受けない。
JSON形式は方式B（貼り付け解析）で引き続き利用できる。
**常に BeginTrans → RollbackTrans で巻き戻すため、UPDATE/DELETE/INSERTを解析してもデータは変更されない。**
ただし ANALYZE はクエリを実際に実行するため、実行負荷そのものは本番にかかる。重いクエリは時間帯に注意。
「設定」シートの「ANALYZE実行=いいえ」にすると EXPLAIN のみ（実行なし・コスト見積ベースの解析）になる。

**セッション設定を変えて試す（チューニング比較）**: SQLの先頭に `SET` 文を書くと、
EXPLAINの前に同一トランザクション内で実行される（ROLLBACKで設定ごと巻き戻るため痕跡は残らない）。

```sql
SET work_mem = '32MB';
SELECT ... （解析対象のSQL）
```

複数のSET文も可（各行を `;` で終端）。適用したSET内容は「実行計画RAW」シートのA2に記録される。

### 方式B: 貼り付け解析（DB接続不要）

1. psql等で実行計画を取得

   ```sql
   -- 推奨（情報量最大）
   EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) SELECT ...;
   -- テキスト形式でも解析可能
   EXPLAIN (ANALYZE, BUFFERS) SELECT ...;
   -- 更新系SQLは必ずトランザクションで包む
   BEGIN; EXPLAIN (ANALYZE, BUFFERS) UPDATE ...; ROLLBACK;
   ```

2. 出力を「実行計画RAW」シートのA4以降に貼り付け
   （psqlの罫線・`QUERY PLAN`ヘッダ・行末の`+`・`(n rows)`はそのままでよい。自動除去する）
3. 「→ 貼り付けた実行計画を解析」ボタンを押す

### 方式D: 改善版クエリの自動生成 → 比較まで一気通貫

1. 「SQL入力」シートに元クエリを入力し、「→ 改善版クエリを生成」ボタンを押す
2. 実行計画の取得・分析後、「改善クエリ案」シートに3点セットが出力される
   - **① 事前実行スクリプト（DDL）**: CREATE INDEX CONCURRENTLY / ANALYZE / VACUUM 等。
     クエリ文には埋め込めない施策。根拠コメント付き。レビューしてから実行すること
   - **② 改善版クエリ**: SET文（work_mem算出値、jit off等）を先頭に織り込んだ実行可能なSQL
   - **③ 手動検討の書き換え候補**: NOT IN→NOT EXISTS、SELECT *、前方ワイルドカードLIKE、
     OFFSETページング等の検出。構造的な書き換えは誤変換リスクがあるため自動適用しない
3. ②は「チューニング比較」シートのC列（元クエリはA列）へ自動投入されるので、
   そのまま「前後を連続実行して比較」ボタンで効果検証できる

### 方式C: チューニングA/B比較

1. 「チューニング比較」シートの A4以降に改善前SQL、C4以降に改善後SQLを入力
   （どちらの欄も先頭のSET文が使える。例: 改善後だけ `SET work_mem = '128MB';` を付ける）
2. 「→ 前後を連続実行して比較」ボタンを押す（両方とも実行後ROLLBACKで巻き戻される）
3. 「比較レポート」シートに以下が出力される
   - 判定バナー: 改善（短縮率・高速化倍率）/ 悪化 / ほぼ変化なし（±5%は計測誤差扱い）
   - サマリ表: 実行時間・プランニング時間・総コスト・ノード数・指摘件数の前後比較
   - ノード差分: 消滅（緑）/ 新規（青）/ 共通ノードの時間変化（変化量の大きい順、±30%超を着色）
   - 指摘の変化: 解消（緑）/ 新規（赤）/ 残存（黄）

ノードの対応付けは「ノード種別＋インデックス＋テーブル」ラベルの一致によるヒューリスティック。
プラン構造が大きく変わった場合（結合順序の入れ替え等）は消滅/新規として現れる。
計測揺らぎがあるため、際どい差は複数回実行して平均で判断すること。

## 出力の見方

### プランツリー シート

- **自ノード時間**: 子ノード分を差し引いた、そのノード自身の消費時間。ヒートマップ（白→黄→赤）で着色
- **時間%**: 実行時間全体に占める割合（データバー表示）。実測なしの場合はコスト比
- **行数誤差**: 見積と実測の乖離。`×46.3 過小` = 実際が見積の46.3倍。3倍以上で黄、10倍以上で赤
- **⚠列**: そのノードに改善提案がある印（●赤=高、●橙=中、○=低）

### 改善提案 シート

重大度（高/中/低）順の指摘一覧。ノード列のリンクでプランツリーの該当行へ飛べる。

検出パターン: 行数見積誤差（統計情報劣化・拡張統計の要否）/ Seq Scanのフィルタ大量除去（インデックス欠如）/ ソートのディスクスピル（work_mem）/ ハッシュのマルチバッチ化 / Nested Loop内側走査の暴走 / lossyビットマップ / 並列ワーカー起動不足 / Index Only ScanのHeap Fetches（VACUUM）/ JIT・トリガのオーバーヘッド / 一時ファイルI/O

## 既知の制限

- **並列プラン（Gather配下）の排他時間は近似値**。ワーカーの実行時間は壁時計上重なるため、厳密な按分はしていない
- CTE/InitPlanが複数箇所から参照される場合、時間の二重計上があり得る
- テキスト形式パーサはPostgreSQL標準の出力形式（インデント＋`->`）を前提とする。`auto_explain`のログ出力はプラン部分だけを貼り付けること
- VBAコードはWindows Excel実機でのみ動作検証可能なため、パーサ・集計アルゴリズムはPython移植版（`verify/crosscheck.py`、全項目PASS）でクロスチェック済み。Excel固有の描画部分（罫線・ボタン等）は実機で初回動作確認を推奨
- 改善提案はヒューリスティクスであり最終判断は人間が行うこと。特に`work_mem`の全体設定変更は接続数×確保量のメモリ影響を必ず試算すること

## 動作確認

`samples/sample_text_plan.txt`（テキスト形式）または `samples/sample_json_plan.json`（JSON形式）を
「実行計画RAW」シートに貼り付けて解析ボタンを押すと、
「Sortディスクスピル(高)」「NestedLoop内側SeqScan暴走(高)」「見積誤差46倍(中)」等が検出されれば正常動作。
